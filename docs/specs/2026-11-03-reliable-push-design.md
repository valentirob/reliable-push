## 1. Architecture

```
Existing notification backend
  │ (1) POST /v1/notifications {userId, message, policy}  ── X-Api-Key ──►  reliable-push API
  │ ◄── 201 {trackingId}
  │ (2) sends push via FCM/APNs with rp_tid = trackingId ─────────────────►  Device
                                                                              │
Device SDK (iOS NSE / Android FCM service)                                    │
  (3) POST /v1/events [{trackingId, DELIVERED, at}]  ── Bearer device JWT ──► API
  (4) POST /v1/events [{trackingId, READ, at}]        (on tap)
                                                                              
reliable-push worker
  (5) every few seconds: claim PENDING rows with due_at <= now (SKIP LOCKED)
      ──► POST <app fallback webhook> {trackingId, userId, fallback, reason, attempt}  (HMAC-signed)
```

**Shape:** a modular monolith (one Spring Boot application, one container image).
Spring profiles select the role: `api` (HTTP endpoints), `worker` (scheduler +
webhook dispatcher), or both (default). Implementation note: only `worker` gates beans (scheduler, webhook client, retention and backlog jobs);
the HTTP endpoints are served by every instance, so `api` means "without `worker`" (see `docs/operations.md`). PostgreSQL is the only stateful
dependency. Integration is **sidecar**: the existing backend keeps sending pushes
and holds the FCM/APNs credentials; reliable-push never does.

**Tenancy:** multi-app, single organisation. Every row is partitioned by `appId`.

### 1.1 Backend modules (`backend/src/main/java/io/reliablepush/...`)

| Module | Responsibility | Public surface |
|---|---|---|
| `apps` | Per-app configuration (keys, OIDC, defaults, webhook) loaded from config | `AppRegistry.find(appId)` |
| `notifications` | Sender API: register, get, cancel | REST `/v1/notifications`, `NotificationService` |
| `devices` | Device registration, device-JWT issue/refresh/revoke, OIDC verification | REST `/v1/devices`, `DeviceTokenService`, `IdentityVerifier` SPI |
| `tracking` | Device events → state transitions | REST `/v1/events`, `TrackingService` |
| `fallback` | Due-row claiming, webhook dispatch, retries | `FallbackScheduler`, `WebhookClient` |
| `shared` | Errors, clock, ids, rate limiting, security filters | — |

Modules call each other only through the listed services, never through
another module's repositories.

## 2. Notification lifecycle

States: `PENDING`, `DELIVERED`, `READ`, `FALLBACK_TRIGGERED`, `FALLBACK_FAILED`, `FALLBACK_EXPIRED`, `CANCELLED`, plus the internal `DISPATCHING` (fallback claimed, webhook in progress or awaiting retry; reported to senders as `FALLBACK_PENDING`).

```
PENDING ──DELIVERED event──► DELIVERED ──READ event──► READ
PENDING ──READ event───────► READ                (READ implies delivered; delivered_at = read_at if unset)
PENDING / DELIVERED ──due & policy unmet──► (dispatching) ──2xx──► FALLBACK_TRIGGERED
                                                        ├─retries exhausted─► FALLBACK_FAILED
                                                        └─trigger window passed─► FALLBACK_EXPIRED
PENDING / DELIVERED ──claimed after trigger window passed──► FALLBACK_EXPIRED   (never dispatched)
PENDING / DELIVERED ──sender cancel──► CANCELLED
```

- **Policy** `NOT_DELIVERED`: satisfied by `DELIVERED` or `READ`. Policy `NOT_READ`: satisfied only by `READ`.
- **Due time:** `due_at = created_at + timeoutMinutes`. Rows whose policy is satisfied get `due_at = NULL` (removed from the partial index).
- **`closed_at`** is the moment no further fallback processing is needed: the policy was satisfied (`DELIVERED` under `NOT_DELIVERED`), `READ`, `CANCELLED`, or a final fallback state. A closed row never has `due_at` (CHECK constraint). A `DELIVERED` row closed under `NOT_DELIVERED` can still become `READ`; its `closed_at` is kept.
- **Race safety:** events update with `UPDATE ... WHERE id = ? AND state IN (<allowed>)`; the worker claims rows with one statement, `SELECT ... FOR NO KEY UPDATE SKIP LOCKED LIMIT n` followed by `UPDATE ... SET state = 'DISPATCHING'` (a single transaction; `FOR NO KEY UPDATE` does not block event inserts that reference the row). Exactly one of "policy satisfied" and "fallback claimed" wins.
- **Claim query:** `(state IN ('PENDING','DELIVERED') AND due_at <= now()) OR (state = 'DISPATCHING' AND next_attempt_at <= now())`. On claim, `next_attempt_at = lease_until = now() + lease` (default 2 min) so a worker that crashes mid-dispatch releases the row automatically; on webhook failure `next_attempt_at = now() + backoff` and `lease_until` is cleared; on success or final failure the row is closed. A row is **reclaimed** when it is claimed while its previous `lease_until` is still set (the previous holder never persisted an outcome: crash, or a call that outlasted the lease); it is logged as `fallback.reclaimed`. Outcome writes (retry scheduled, closed) are **fenced** on the `lease_until` the worker claimed with, so a stale worker can never overwrite the outcome of the worker that re-claimed the row. A crash after the webhook succeeded but before the outcome was written can re-send once; receivers de-duplicate with `Idempotency-Key`. Re-sends after a crash are not counted against `max-attempts` (the attempt count is persisted only with an outcome).
- **Apps missing from the configuration:** a due row whose `appId` is not configured on this instance (for example during a rolling deploy that adds an app) is left for later (re-claimable after one lease, attempts unchanged) until `due_at` + 20 min, then closed as `FALLBACK_EXPIRED` with reason `app_not_configured`.
- **Trigger window (stale-fallback guard):** a fallback may only be dispatched while `now() <= due_at + triggerWindowMinutes` (per app, default 20; must be ≥ the cumulative retry backoff). This applies to every attempt — the first one, retries, and re-claims after a worker crash or outage. A row claimed outside the window is closed as `FALLBACK_EXPIRED` without calling the webhook, and logged as `fallback.expired`. Retries whose next backoff would fall outside the window are not scheduled; the row expires instead. The original `due_at` is kept (not moved by retries) so the window is measured from when the trigger should have started.
- **Late events** (after fallback claimed) are stored in `notification_event` with `late = true`; the state does not change.
- **Duplicates** (same `trackingId` + type) are no-ops returning success.
- **Multi-device:** events from any active device of the same `appId` + `userId` count.

## 3. Data model (PostgreSQL, Flyway)

```sql
notification(
  id uuid pk,                       -- trackingId
  app_id text not null,
  user_id text not null,
  external_id text null,            -- sender's own id, unique per app when present
  policy text not null,             -- NOT_DELIVERED | NOT_READ
  timeout_minutes int not null,
  fallback_payload jsonb not null,  -- message for the fallback channel (opaque to us, size-bounded)
  state text not null,
  created_at timestamptz not null,
  due_at timestamptz null,
  delivered_at timestamptz null,
  read_at timestamptz null,
  fallback_attempts int not null default 0,
  next_attempt_at timestamptz null,
  lease_until timestamptz null,     -- V3: set by a claim, cleared when the worker persists an outcome
  closed_at timestamptz null
)
check (closed_at is null or due_at is null)                 -- V2: a closed row never waits for the worker
check (lease_until is null or state = 'DISPATCHING')        -- V3: only a claimed row holds a lease
index notification_due on notification(due_at) where due_at is not null
index notification_retry on notification(next_attempt_at) where state = 'DISPATCHING'
index notification_app_user_created on notification(app_id, user_id, created_at desc)
index notification_closed on notification(closed_at) where closed_at is not null
unique (app_id, external_id) where external_id is not null

notification_event(
  id bigserial,
  notification_id uuid not null references notification(id) on delete cascade,
  device_id uuid null references device(id) on delete set null,   -- history survives a purged device
  type text, occurred_at timestamptz, received_at timestamptz, late bool,
  unique (notification_id, type)                                  -- V2: duplicates are ON CONFLICT DO NOTHING
)
device(id uuid pk, app_id, user_id, platform text, token_version int, created_at, last_seen_at, revoked_at null)
```

Retention: a daily job deletes closed notifications and their events older than
`retentionDays` (default 30).

## 4. APIs (OpenAPI 3, contract-first in `backend/src/main/resources/openapi.yaml`)

### 4.1 Sender API — header `X-Api-Key` (per app, stored as SHA-256 hash)

| Method | Path | Body / result |
|---|---|---|
| `POST` | `/v1/notifications` | `{userId, externalId?, policy?, timeoutMinutes?, fallback:{...}}` → `201 {trackingId, dueAt}` |
| `GET` | `/v1/notifications/{trackingId}` | → `{state, createdAt, deliveredAt, readAt, ...}` |
| `GET` | `/v1/notifications?userId=&state=&since=&limit=&cursor=` | → `{items:[...], nextCursor}` (newest first, `limit` ≤ 100, scoped to the API key's app) |
| `DELETE` | `/v1/notifications/{trackingId}` | cancel → `204` (409 if already closed) |

`appId` comes from the API key, never from the body. `POST` with an existing
`externalId` returns the existing record (idempotent).

### 4.2 Device API

| Method | Path | Auth | Body / result |
|---|---|---|---|
| `POST` | `/v1/devices` | OIDC ID token in body | `{appId, idToken, platform, deviceId?}` → `201 {deviceId, deviceToken, expiresAt}` |
| `POST` | `/v1/devices/token:refresh` | device JWT | → `{deviceToken, expiresAt}` |
| `DELETE` | `/v1/devices/me` | device JWT | revoke → `204` |
| `POST` | `/v1/events` | device JWT | `{events:[{trackingId, type, occurredAt}]}` (max 50) → `200 {accepted, ignored}` |

### 4.3 Errors
RFC 9457 problem+json. `401` invalid credentials, `404` unknown id (also an id of
another app), `409` invalid state, `413`/`422` validation, `429` rate limited with
`Retry-After`, `503` identity provider keys unavailable (with `Retry-After`).
For `POST /v1/events` the outcome is reported per item in the `200` response
(`ACCEPTED`, `DUPLICATE`, `LATE`, `NOT_FOUND`, `FORBIDDEN`): a trackingId of another
user is `FORBIDDEN` (logged as `authz.denied`), one of another app is `NOT_FOUND`.

## 5. Security

- **Device identity:** `IdentityVerifier` SPI. Default `OidcIdTokenVerifier` accepts RS256 and ES256 only, with keys taken only from the issuer's JWKS (never from token headers; `azp` is ignored by design), and validates `iss`, `aud`, `exp` (`iat`/`nbf` with 60 s skew); it maps a configured claim (default `sub`, at most 256 characters) to `userId`. ID tokens larger than 8 KB are rejected. The JWKS URL is `jwks-uri` or the `jwks_uri` of the discovery document; it must be https (http only when the issuer host is `localhost`/`127.0.0.1`); redirects are not followed. The key set is cached for 15 minutes, a token with an unknown `kid` may refresh it at most once per 30 s, stale keys keep being served during an identity provider outage, fetches have a 5 s deadline and a 64 KB limit. If no key set can be obtained, `POST /v1/devices` answers `503` with `Retry-After: 30`. Alternative `SignedGrantVerifier`: short-lived HS256 grant signed by the customer backend with a shared secret of at least 32 bytes; lifetime (`exp - iat`) at most 5 minutes, so a leaked grant can be replayed for at most about 7 minutes (no `jti` store).
- **Device JWT:** ES256, signed with a backend key; keys are PEM pairs per `kid` (rotation: see §8). Claims: `iss`, `aud=appId`, `sub=userId`, `did=deviceId`, `ver=token_version`, `iat`, `exp`. Validity per app (default 90 days). Verification is strict (algorithm, `kid` from configuration only, single `aud`). Revocation: `device.revoked_at` or bumped `token_version`, checked with a short in-memory cache (`revocation-cache-ttl`, default 60 s).
- **Event authorisation:** `notification.app_id = jwt.aud AND notification.user_id = jwt.sub`, else the event is reported per item as `FORBIDDEN` (another user's notification; logged as `authz.denied`) or `NOT_FOUND` (unknown id or another app) inside the `200` response (see §4.3).
- **Rate limiting:** Bucket4j in-memory token buckets per `deviceId` and per app API key (defaults: device 60 req/min, sender key 6,000 req/min). Registration has no device token yet and is limited per user (`register:<appId>:<userHash>`, the device-per-minute limit), counted only after the credential was verified, so unauthenticated traffic cannot exhaust a legitimate user's bucket. Limits are per instance (N replicas allow N times the rate); per-IP limits for unauthenticated traffic belong at the ingress. Interface allows a shared store later.
- **Webhook:** headers `X-RP-Timestamp`, `X-RP-Signature: v1=<hex HMAC-SHA256(secret, timestamp + "." + body)>`, `Idempotency-Key: <trackingId>`. Retries: max 5 attempts with exponential backoff between them (1, 2, 4, 8 min), configurable; per-attempt HTTP timeout 10 s. Only `2xx` is success; `4xx` other than `408/429` is final failure.
- **Hygiene:** Bean Validation on all inputs, `fallback` payload ≤ 4 KB, request body ≤ 64 KB, no tokens or payloads in logs, TLS terminated at ingress.

## 6. Push payload contract (customer backend → device)

The tracking id key is `rp_tid` (string UUID). Policy and timeout are not sent to the device.

- **iOS (APNs):** `aps.alert` present **and** `aps.mutable-content = 1`; `rp_tid` at the top level of the payload.
- **Android, mode v1 (default, GA):** data-only message (`data.rp_tid`, `data.title`, `data.body`, optional `data.*`), `android.priority = HIGH`. The SDK reports `DELIVERED` and **always** posts a visible notification.
- **Android, mode v2 (opt-in):** `AndroidConfigV2` `RemoteNotification` with `mutable_content: true` and `rp_tid` in its data; SDK implements `onNotificationReceived` and returns a `NotificationResponse` within 20 s (requires firebase-messaging ≥ 26.1.0-eap01; older devices fall back to v1 `onMessageReceived`).

Pushes sent in another shape are not tracked → they end in fallback (by design: "unknown" ⇒ fallback).

## 7. Mobile SDKs (cycles 2 and 3)

### 7.1 Common API
- `configure(baseUrl, appId)`
- `register(idToken)` — on login / app open; stores device token securely.
- `handle(message)` — called from the push entry point; returns quickly.
- `trackOpen(notification)` — called on tap.
- `logout()` — revokes and clears.

Token logic: decode `exp` locally; refresh when remaining < 20% of validity or
on `401`; never refresh more than once per app launch. Events that fail to send
are persisted and retried in a batch (Android `JobScheduler` with network
constraint; iOS on next app launch or next NSE run). No polling, no periodic jobs.
SDK logging uses the platform logger (`android.util.Log` / `OSLog`) with the same
event names as the backend (e.g. `tracking.event_sent`, `token.refreshed`),
off below WARN in release builds, never logging tokens or notification content.

### 7.2 Android (`android/`, Kotlin, minSdk 26, AAR on Maven Central)
- `ReliablePushMessagingService` helper delegating from the host's `FirebaseMessagingService` (v1) and `onNotificationReceived` (v2).
- Storage: device token encrypted with an Android Keystore AES-GCM key, stored in private SharedPreferences (no `androidx.security-crypto`).
- Pending-event retry via platform `JobScheduler` with a network constraint (no WorkManager); HTTP via `HttpURLConnection`, JSON via `org.json`.
- Respects `POST_NOTIFICATIONS` (Android 13+); documents Play Data Safety entries.

### 7.3 iOS (`ios/`, Swift, iOS 15+, Swift Package)
- `ReliablePushExtension` helper for the host's `UNNotificationServiceExtension`: reads `rp_tid`, sends `DELIVERED` with a short timeout, always calls the content handler (also from `serviceExtensionTimeWillExpire`).
- Device token in a shared Keychain access group + App Group so app and NSE share it.
- `READ` from `UNUserNotificationCenterDelegate.didReceive(response:)`.
- Ships `PrivacyInfo.xcprivacy`; documents App Store privacy labels.

Known limits (documented): no tracking if the user disabled notifications, the
Android app was force-stopped, or the device lacks Google Play services; all end
in fallback.

## 8. Configuration (example)

```yaml
reliable-push:
  device-token:
    signing-keys:                             # ES256 (P-256) key pairs, PEM in environment variables
      - kid: k1
        private-key-pem-ref: env:RP_DEVICE_KEY_K1      # PKCS#8 ("BEGIN PRIVATE KEY")
        public-key-pem-ref: env:RP_DEVICE_PUB_K1       # SPKI ("BEGIN PUBLIC KEY")
    current-kid: k1                           # signs new tokens; older kids still verify
    revocation-cache-ttl: 60s
  worker:
    poll-interval: 5s
    batch-size: 100                         # rows per claim; a tick claims again while claims come back full (≤ lease/2)
    max-concurrency: 100                    # webhook calls in flight per worker (default: batch-size)
    lease: 2m
  retention-days: 30
  apps:
    shop:
      sender-api-key-sha256: "<hash>"
      identity: { type: oidc, issuer: "https://idp.example.com", audience: "shop-mobile", user-claim: sub }
      device-token-validity: 90d
      default-policy: NOT_DELIVERED
      default-timeout-minutes: 10
      fallback: { url: "https://fallback.example.com/hook", hmac-secret-ref: env:RP_SHOP_HOOK_SECRET, max-attempts: 5, trigger-window-minutes: 20 }
```

Secret and key references are always `env:NAME`, read literally from the environment (no `${...}` indirection; inline
secrets are rejected at startup). Generate a key pair with
`openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -pkeyopt ec_param_enc:named_curve -out k1.pem` (private key, PKCS#8; `ec_param_enc:named_curve` is required with macOS LibreSSL 3.3.x, which otherwise writes explicit EC parameters that the backend rejects at startup)
and `openssl pkey -in k1.pem -pubout -out k1.pub.pem`. Rotation: add a new pair, switch `current-kid`, keep the old pair
until the longest `device-token-validity` has elapsed, then remove it. The full reference is `docs/operations.md`.

## 9. Operations

- Java 21 (virtual threads), Spring Boot 4.x, Maven wrapper, Flyway, Actuator (`/actuator/health/{liveness,readiness}`), Micrometer Prometheus.
- Metrics: `rp_notifications_registered_total`, `rp_events_total{type,late}`, `rp_fallback_total{outcome=triggered|failed|expired}`, `rp_webhook_latency_seconds`, `rp_due_backlog`.

### 9.1 Logging

- **Framework:** Log4j 2 via `spring-boot-starter-log4j2` (Logback excluded); application code logs through the Log4j 2 API (or SLF4J bound to Log4j 2). Async loggers are not required; keep the default synchronous appender unless load tests show otherwise.
- **Format:** profile-selected in `log4j2-spring.xml`:
  - `json` (default in containers): one JSON object per line on stdout, `JsonTemplateLayout` with the project template `log4j2/ecs-reliable-push.json`, derived from the bundled **Elastic Common Schema** `EcsLayout.json` (catalogue fields such as `event.action` and `rp.*` are top-level keys; any other ThreadContext entry goes under `labels.*`), ready for Cloud Logging, OpenShift logging / EFK, Loki.
  - `local`: `PatternLayout` `%d{ISO8601} %-5level [%t] %c{1.} [trace=%X{trace.id}] - %m%n%throwable`.
- **Correlation:** a servlet filter reads the W3C `traceparent` header (or `X-Request-Id`), otherwise generates an id, puts it in the `ThreadContext` (`trace.id`) and returns it as `X-Request-Id`. The worker sets a new `trace.id` per claimed row and adds `rp.tracking_id`, so one notification can be followed across API and worker logs.
- **Common fields** (ECS names, plus an `rp.*` namespace): `@timestamp`, `log.level`, `log.logger`, `message`, `service.name`, `service.version`, `trace.id`, `event.action`, `event.outcome` (`success|failure|unknown`), `event.duration` (ns), `http.request.method`, `url.path` (template, e.g. `/v1/notifications/{id}`), `http.response.status_code`, `rp.app_id`, `rp.tracking_id`, `rp.device_id`, `rp.user_hash` (truncated SHA-256 of `userId`; raw user ids are not logged).
- **Never logged:** API keys, ID tokens, device JWTs, HMAC secrets, webhook signatures, fallback message content, request/response bodies.
- **Event catalogue** (`event.action`; one INFO line each unless noted):

| Event | Emitted when |
|---|---|
| `api.request` | every HTTP request completes (access log: method, path template, status, duration, app, outcome) |
| `notification.registered` / `notification.duplicate` / `notification.cancelled` | sender API |
| `device.registered` / `device.token_refreshed` / `device.revoked` | device API |
| `tracking.event_accepted` (with `rp.event_type`, `rp.late`) / `tracking.event_ignored` (duplicate) | `/v1/events` |
| `auth.failed` (WARN, reason code only) / `authz.denied` (WARN) / `rate_limit.exceeded` (WARN) | security filters |
| `fallback.claimed` / `fallback.dispatched` / `fallback.retry_scheduled` (WARN for an app missing from the configuration) / `fallback.failed` (WARN) / `fallback.expired` (WARN) / `fallback.reclaimed` (WARN, lease expired → previous worker crashed) | worker |
| `retention.purged` | retention job (count only) |

- `EventLog` throws only for programming errors (deny-listed keys such as `token`, `userId`, `message`, or keys reserved by the template); data-dependent conflicts (for example an `rp.*` field that differs from the ThreadContext value) never break a request: the ThreadContext value wins and a warning naming only the key goes to Log4j's status logger.
- Levels: INFO for the catalogue, WARN for security and degraded outcomes, ERROR only for unexpected exceptions (with stack trace), DEBUG off by default. Log levels configurable at runtime via environment (`LOGGING_LEVEL_*`).

### 9.2 Dependency budget ("lightweight")

The backend, the sender client and the mobile SDKs avoid heavy frameworks. Any new dependency needs a justification in the PR and must fit this budget.

| Component | Allowed | Not allowed |
|---|---|---|
| Backend service | Spring Boot web (embedded Tomcat), Spring JDBC (`JdbcClient`), Actuator + Micrometer Prometheus, Flyway, PostgreSQL driver, Log4j 2 (+ `log4j-layout-template-json` for ECS), Bean Validation, `nimbus-jose-jwt` (JWT/JWKS), Bucket4j core | JPA/Hibernate, Spring Security, Spring Cloud, Lombok, MapStruct, reactive stack, message brokers |
| Sender client `client-java/` (optional helper for existing backends) | JDK 17+ only (`java.net.http.HttpClient`), hand-written JSON for its fixed small schema | any runtime dependency |
| Android SDK | Kotlin stdlib, Android platform APIs (`HttpURLConnection`, `org.json`, Keystore AES-GCM, `JobScheduler`); `firebase-messaging` as `compileOnly` (host app provides it) | OkHttp/Retrofit, coroutines, WorkManager, DI frameworks, Gson/Moshi, `androidx.security-crypto` (deprecated) |
| iOS SDK | Foundation, UserNotifications, Security (Keychain), OSLog | any third-party package |

Size targets (checked in CI from cycle 2/3): Android AAR < 100 KB, iOS framework < 300 KB; backend container image < 250 MB.

Authentication filters are implemented as small servlet filters on top of `nimbus-jose-jwt` instead of Spring Security; they are covered by dedicated unit and integration tests and by the security reviewer role.
- Container: a jlink-trimmed Temurin 21 JRE on a pinned Alpine (about 105 MB uncompressed; the budget is measured as the sum of the uncompressed layer sizes), non-root, writable dirs only under `/tmp`, works with OpenShift arbitrary UIDs.
- Deploy: Helm chart (`deploy/helm/reliable-push`) with values for GKE and OpenShift (Route instead of Ingress, no fixed UID); separate `api`/`worker` deployments optional (`mode: split`); probes and metrics on the management port 8081. Guide: `docs/deployment.md`.

## 10. Testing strategy

| Level | Tooling | Covers |
|---|---|---|
| Unit | JUnit 5, AssertJ | state machine, policy evaluation, token logic, HMAC, validation |
| Integration (`*IT`) | Testcontainers PostgreSQL, WireMock (OIDC JWKS, webhook) | REST endpoints, SKIP LOCKED claiming with concurrent workers, retries, rate limits |
| Contract | OpenAPI validation of requests/responses in ITs | API drift |
| End-to-end (local only, §10.1) | `harness/` + docker-compose | full scenarios across components |
| Load (local only, `loadtest/`, `./scripts/load.sh`) | Gatling Java DSL in a container on the harness compose network | NFR-2 (API ingest), worker burst drain |
| Mobile (cycles 2–3) | JUnit/Robolectric, XCTest; emulator/simulator instrumented tests against the harness | SDK logic, NSE/service handling |

**Harness (`harness/`):** signed-grant identity (the harness signs the grants devices register with; no fake OIDC issuer), fake
sender (registers notifications), fallback receiver (verifies HMAC, records
calls), device simulator (registers devices, sends DELIVERED/READ with
configurable delay/loss), and a scenario runner that asserts outcomes:
delivered before timeout, read policy, not delivered → exactly one fallback,
late delivery, multi-device, cancellation, token refresh near expiry, rate
limiting, worker crash during dispatch inside the trigger window (re-sent once)
and outside it (`FALLBACK_EXPIRED`, webhook not called), and log assertions
(every API call and trigger step produces its catalogue event; no secrets in logs).

### 10.1 Local end-to-end runs and the feedback loop

End-to-end tests run **on a local PC**, started either manually by a developer
or by an AI agent (Claude Code, Antigravity, others) as part of its feedback
loop. They are **not** executed in CI; CI runs unit, integration and contract
tests only.

- **One entry point**, same for humans and agents: `./scripts/e2e.sh [--scenario <name>] [--keep]`
  (Windows: `scripts/e2e.ps1`). It builds the images, starts
  `harness/compose/docker-compose.yml` (backend API and two workers, PostgreSQL,
  harness with fallback receiver, device simulator and signed-grant identity), waits for health, runs the scenarios, collects
  logs, and tears everything down unless `--keep` is given.
- **Prerequisites:** Docker Desktop or Podman with compose, JDK 21. Mobile
  E2E (cycles 2–3) additionally needs a local Android emulator / Xcode iOS
  simulator; those scenarios run against the same local harness.
- **Fast clock:** the `e2e` and `demo` Spring profiles enable
  `reliable-push.testing.minute-duration` (e.g. `1s`), so a "10 minute" timeout
  takes 10 s and the full suite runs in a few minutes. It scales the notification timeout,
  the trigger window, the webhook backoff and the worker lease alike; the webhook
  `http-timeout` is a literal duration and is never scaled (outside the fast clock the lease must exceed it). The property is rejected
  at startup in any other profile, so it cannot leak into production. The same
  two profiles also write the backend JSON log to a shared volume for the
  harness (stdout logging is unchanged).
- **Machine-readable results** for agents: exit code `0` = all passed; JUnit XML
  in `harness/build/e2e/junit/`; a summary `harness/build/e2e/summary.json`
  (`{scenario, status, durationMs, failure: {expected, actual, hint}, logs}`);
  container logs in `harness/build/e2e/logs/`. Output is deterministic (fixed
  seeds, no wall-clock dependent assertions beyond the scaled clock).
- **Agent feedback loop** (`.agents/skills/run-e2e`): run → read `summary.json`
  → for each failure reproduce it with the smallest failing unit/integration
  test → fix → rerun the failed scenario → rerun the full suite. Max 3
  iterations, then stop and record the remaining failures in `docs/STATUS.md`.
  Improvements the agent notices (flaky scenario, missing coverage, slow step)
  are recorded as plan tasks, not silently changed.
- **When it must run:** before merging any `feature/*` that touches `backend/`,
  `harness/`, `android/` or `ios/` into `develop`, and before closing a
  `release/*`. The merge commit or PR description states the result
  (`E2E: 17/17 passed, scripts/e2e.sh, <date>`).

### 10.2 Harness web console (manual testing and demo)

A browser console, part of the harness, to run manual tests, simulate pushes and
show delivery tracking live. It is a **local test/demo tool only**: never built
into the backend image, never deployed with the Helm chart, so it adds no
production attack surface.

**Start:** `./scripts/demo.sh [--realtime]` (Windows `scripts\demo.ps1`) starts
the harness compose stack (Spring profile `demo` through `demo.override.yml`) and opens
`http://127.0.0.1:8090/`. Default is the fast clock (1 "minute" = 1 s,
§10.1); `--realtime` uses real minutes for live demos with real timing. Ports
bind to `127.0.0.1` only. A permanent banner reads "Test harness — simulated
data, not for production".

**Architecture:**

```
Browser (static HTML/CSS/JS) ──REST + SSE──► harness-control (:8090)
                                               ├─► backend sender API  (/v1/notifications, harness API key)
                                               ├─► backend device API  (via device simulator, signed-grant identity)
                                               ├─► fallback receiver   (inbox + failure-mode switch)
                                               └─► backend JSON log file (shared volume, demo/e2e profiles only)
```

- **Frontend:** plain HTML, CSS and ES-module JavaScript served as static files
  by `harness-control`; **no build step, no npm runtime dependencies**, no
  framework. Works in current Chrome, Firefox, Safari, Edge.
- **`harness-control`:** a small Spring Boot app in `harness/` (same dependency
  budget as the backend) that orchestrates the simulators and exposes
  `/console/api/*` plus one Server-Sent Events stream `/console/api/stream`. It
  polls the backend once per second for active notifications (one poller,
  whatever the number of browser tabs) and pushes changes over SSE.

**Screens / features:**

1. **Devices** — create simulated users and devices (iOS / Android, mode v1 or
   v2), register them through the real device API, show device-token expiry and
   trigger a refresh. In cycles 2–3 the sample apps running on a local
   emulator/simulator also appear here as real devices.
2. **Send push** — form for `userId`, message, policy (`NOT_DELIVERED` /
   `NOT_READ`), timeout, and per-device behaviour: deliver after *n* s, read
   after *m* s, never, offline then late delivery. Shows the exact payload the
   customer backend would send for APNs, FCM v1 and FCM v2 (copyable), to
   document the payload contract (§6).
3. **Live tracking** — table of notifications with state badges and countdowns
   to `due_at` and to the end of the trigger window; detail view with a
   timeline: registered → push simulated → DELIVERED (device) → READ →
   fallback claimed / dispatched / retried / expired / cancelled. Cancel button
   calls the real sender API.
4. **Fallback inbox** — webhooks received by the fallback receiver with HMAC
   verification result, attempt number and `Idempotency-Key`; switch to make
   the receiver fail (HTTP 500, timeout) to demonstrate retries,
   `FALLBACK_FAILED` and `FALLBACK_EXPIRED`.
5. **Scenarios** — run any E2E scenario (§10) from the console and watch it
   live; result shown with the same data as `summary.json`.
6. **Logs** — tail of the backend ECS JSON logs, filterable by `trace.id`,
   `rp.tracking_id` and `event.action`, to show the logging catalogue (§9.1).

**Backend support needed:** a list endpoint on the sender API (§4.1,
`GET /v1/notifications`), useful to real senders as well. No console-specific
endpoint is added to the backend.

**Tests:** `harness-control` REST/SSE integration tests; a `console-smoke` E2E
scenario drives the UI headless with Playwright for Java (test-scope
dependency of the harness only): register a device, send a push, see
`DELIVERED`, see a fallback in the inbox.

**Real pushes (cycles 2–3, optional):** a "real sender" mode can send through
FCM/APNs with credentials from a local, git-ignored `.env`, to demo the sample
apps on real or emulated devices. Credentials are never committed or logged.
