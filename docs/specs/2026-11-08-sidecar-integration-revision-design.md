## 0. Purpose and decisions

The sidecar stays: the existing backend keeps sending pushes with its own APNs and FCM credentials. The review of the
design showed three problems:

1. The sender has to know the payload rules (`rp_tid`, `mutable-content`, Android data-only messages) and wait for
   reliable-push to return the tracking id before every tracked send.
2. The device SDKs renew the device token on the receive path, which adds network calls before an iOS notification
   is shown.
3. On Android the SDK posts the notification itself (data-only messages), so an SDK bug can hide a tracked
   notification. The documentation wrongly says the SDK never hides one.

Delivery tracking on the device is invasive by nature, whoever sends the push: an iOS Notification Service Extension
and Android data messages with a local notification are the only ways to run code when a push arrives in the
background. Commercial services with confirmed delivery work the same way (Catapush, OneSignal, Braze, Airship).
Firebase offers nothing lighter today: BigQuery delivery export is daily, Analytics events are batched, and
`AndroidConfigV2` (the Android counterpart of the iOS extension) is a preview SDK outside public Maven, with no GA date.

Decisions taken with the maintainer:

| # | Decision |
|---|---|
| D1 | The sidecar model stays. A push gateway mode is out of scope until the sender teams say how much they can change. |
| D2 | A new standalone, zero-dependency **payload jar** (Java 8+) builds or decorates the APNs and FCM payloads and generates the tracking id. The sender no longer needs to know the payload rules. |
| D3 | The **tracking id is generated by the sender** (by the jar). The sender registers the notification **before** sending, with a short timeout (1 s recommended), and **sends the push with `rp_tid` whatever the registration outcome**. A lost response cannot cause a duplicate fallback, and a failed registration only means no fallback. There is no buffer for early events. |
| D4 | **Tracking and fallback only for users with a registered device.** If the user has no active device for the app, the registration is stored closed with the new final state `NO_DEVICE_REGISTERED` and no fallback is ever scheduled. |
| D5 | **The receive path never renews the device token**: not in the iOS extension, not in the Android receiver, not in any queue flush. Token renewal happens only in the new asynchronous `ensureRegistered`, which the app calls wherever it chooses. |
| D6 | **A 90-day grace period for expired device tokens on `POST /v1/events` and `DELETE /v1/devices/me` only.** Without it, a user who does not open the app for about 90 days would get a fallback for every notification they did see. |
| D7 | **iOS: bounded wait (I1).** The extension records and sends `DELIVERED` first, then hands the notification back when the send ends or when `extensionSendTimeout` expires. The default timeout drops from 5 s to 2 s. Background `URLSession` is rejected: no timing guarantee, host app woken in the background, loss of control. |
| D8 | **Android: the SDK keeps posting the notification (A0), hardened.** It is documented as the market standard. `DELIVERED` is persisted before the notification is posted. A post failure then means a missed fallback, which the maintainer prefers to a duplicate one. |
| D9 | **Display never depends on tracking.** Every SDK entry point catches every error. On an internal error iOS hands back the original content at once and Android posts the simplest notification it can. |
| D10 | Docs, diagrams and presentation explain the sender's duties, the extension's behaviour and the Android data message plus local notification. The false "never hides" statement is corrected. |

Out of scope: push gateway mode; `AndroidConfigV2` (TODO 2.1 stays, and the payload jar becomes the place where the
switch will happen); a buffer for events that arrive before their registration; a batch registration endpoint;
payload libraries for languages other than Java (golden test vectors cover them, see section 4.5).

## 1. The sender flow

```
for each push that needs tracking:
  1. tid  = TrackingIds.newId()                         payload jar, local, no network
  2. POST /v1/notifications {trackingId: tid, userId, policy?, timeoutMinutes?, externalId?, fallback}
        timeout 1 s (recommended), result is informative only
  3. payload = ApnsPayloads / FcmPayloads (build or decorate, with tid)
  4. send the push through the sender's own APNs / FCM client, always
pushes that need no tracking: unchanged, no call to reliable-push, no rp_tid
```

Outcomes of step 2, and what happens:

| Step 2 result | Push sent? | Tracking | Fallback |
|---|---|---|---|
| `201`, state `PENDING` | yes, with `rp_tid` | yes | if the policy is unmet when due |
| `201`, state `NO_DEVICE_REGISTERED` | yes, with `rp_tid` (harmless) | no | never; the sender may send its own SMS |
| `4xx` (validation, auth) | yes, with `rp_tid` | no (unknown id, ignored) | never; a sender bug to fix |
| timeout / `5xx` / network error, row **not** stored | yes, with `rp_tid` | no | never (missed fallback, accepted) |
| timeout, row **stored** (response lost) | yes, with `rp_tid` | yes | as for `PENDING`: no duplicate |
| retry of step 2 with the same `tid` | — | same row (idempotent) | once |

Accepted residual case: the timeout fires, the push is sent and delivered, and the registration commits only after the
`DELIVERED` event arrived. That event got `NOT_FOUND` and is dropped, so a fallback fires that was not needed. It
needs a registration slower than both the timeout and the whole APNs/FCM delivery. It is documented, and the
`rp_notification_registration_seconds` histogram shows how close an installation comes to it.

## 2. Backend changes

### 2.1 `POST /v1/notifications`

- New **required** request field `trackingId` (UUID string), generated by the sender. Missing or not a UUID: `400`
  problem naming the field `trackingId` (maintainer ruling 2026-11-08: no backward compatibility, nothing is deployed).
- Idempotency: a request whose `trackingId` already exists **for the same app** returns the existing record (`201`).
  A `trackingId` that exists for another app returns `409`. A request whose `externalId` already belongs to a row with
  another `trackingId` returns `409` (also when the request's `trackingId` matches a second existing row). The stored
  row's other fields are not compared: the first registration wins. Two concurrent requests with the same
  `trackingId` produce one row and two `201` answers with the same state (`insert ... on conflict do nothing`, then a
  re-read).
- `externalId` stays optional.
- **Device check (D4).** Before inserting, the backend checks that the user has at least one active device for the
  app (2.3). If none, the row is inserted with state `NO_DEVICE_REGISTERED`, `closed_at = created_at`,
  `due_at = null`. The response is `201` with that state. Log `notification.no_device_registered` (INFO, user hash
  only); metric `rp_notifications_registered_total{outcome="no_device_registered"}`.
- New metric `rp_notification_registration_seconds` (histogram of the endpoint's server time).

### 2.2 New final state `NO_DEVICE_REGISTERED`

Added to the `NotificationState` enum (OpenAPI), the `notification_state_check` constraint, the admin dashboard
filters and counts, the harness console, and `client-java`'s `NotificationState`. It is final like `CANCELLED`:
`DELETE /v1/notifications/{trackingId}` answers `409` as for any closed row and leaves the row unchanged, and events for
it are stored with outcome `LATE` (FR-11 semantics: recorded, no effect). A device registered later does not reopen
it. The fallback worker never sees it (`due_at` is null).

The admin overview and daily statistics count it as `noDeviceRegistered` (part of `registered`) and leave it out of
the rate denominators: `n = registered - cancelled - noDeviceRegistered`. The circuit breaker's cohort and resumed
reads leave it out too, so many users without a device cannot open an app's circuit.

### 2.3 Active device

A device is active for `(app_id, user_id)` when `revoked_at is null` and
`token_expires_at + device-token-events-grace > now` (`now` from the application clock). The migration adds
`token_expires_at timestamptz not null` to `device`, backfilled as `last_seen_at` + 90 days (ruling 2026-11-08: no
nullable column). Register and re-register set it to the issued token's `exp`; refresh moves it forward to the new
token's `exp`. The query uses the existing `device_app_user` index.

### 2.4 Grace period for expired device tokens

- New per-app setting `device-token-events-grace` (days, default 90, 0 disables), next to `device-token-validity`.
- `DeviceAuthFilter` accepts a token whose `exp` is in the past by at most the grace **only** on `POST /v1/events` and
  `DELETE /v1/devices/me`. Signature, issuer, version and revocation checks are unchanged. `POST
  /v1/devices/token:refresh` still requires an unexpired token: past expiry the app re-registers with an ID token.
- Risk, documented in `docs/security.md`: a stolen token keeps working for at most `validity + grace` after its last
  refresh. It can only send `DELIVERED`/`READ` for its own user's notifications, which suppresses that user's fallbacks
  and nothing else.
- Log field `token_state` (`valid` or `grace`) on `tracking.events_received`; metric
  `rp_events_total{token="grace"}`.

### 2.5 Unchanged

The events endpoint, the outcomes (`ACCEPTED`, `DUPLICATE`, `LATE`, `NOT_FOUND`, `FORBIDDEN`), the fallback worker,
the webhook and the admin API (except the new state value).

## 3. Mobile SDKs

### 3.1 Principles, both platforms (D5, D9)

1. The receive entry point first reads `rp_tid`. Without a valid one it returns at once and reads nothing else
   (already true on both platforms; iOS since 3f269e4). Tests keep it so.
2. With a valid `rp_tid`: read the stored configuration and device token. Not configured or not registered: show the
   notification, record nothing (WARN `tracking.not_registered`).
3. Gate: the notification will actually be shown (iOS notification settings; Android notifications enabled, channel
   present and not blocked). Not shown: show anyway (the OS decides), record nothing.
4. Persist `DELIVERED`, then send it at once: **one** `POST /v1/events` with the stored token, **no refresh** before
   or after.
5. Response handling without refresh. `200` removes acknowledged items as today. `401` keeps the event queued and sets
   the stored flag `renewalNeeded`. Network errors and `5xx` keep the event queued.
6. Every public entry point catches every `Throwable`/error from SDK code, logs WARN `sdk.internal_error` (class
   name only) and continues with the display path. No SDK error ever reaches the host's code as an exception.
7. Queued events are sent later by the app (`configure` at launch, and Android's retry job), also without refresh.

### 3.2 `ensureRegistered` (both platforms)

```swift
// iOS
public static func ensureRegistered(idTokenProvider: @escaping @Sendable () async -> String?,
                                    completion: (@MainActor @Sendable (RegisterResult) -> Void)? = nil)
public static func ensureRegistered(idTokenProvider: @escaping @Sendable () async -> String?) async -> RegisterResult
```

```kotlin
// Android
public fun ensureRegistered(idTokenProvider: (deliver: (String?) -> Unit) -> Unit, callback: ((RegisterResult) -> Unit)? = null)
```

Android ruling (plan, Task 6): the SDK has no coroutines dependency and NFR-10 forbids adding one, so the provider is a
callback instead of a `suspend` function. It calls `deliver` exactly once, from any thread; extra calls are ignored.
If `deliver` is not called within 30 s, the run ends `NotLoggedIn`. `callback` runs on the main thread, as for
`register`.

- Returns at once. The work runs on the SDK's background queue/thread and never blocks app start-up. Only one run at a
  time: a call while one is in progress joins it.
- Local decision, no network unless needed, evaluated in this order:
  1. no device token, or the stored token is expired → **ID-token path**: call `idTokenProvider`; `null` → result
     `notLoggedIn` and nothing else; a token → `POST /v1/devices` (register);
  2. token unexpired and (`renewalNeeded` is set, or less than 20 % of its validity is left) →
     `POST /v1/devices/token:refresh`; a `401` there → ID-token path;
  3. otherwise → result `alreadyRegistered`, no call.
- `renewalNeeded` is stored next to the token (iOS: App Group storage shared with the extension; Android: the SDK's
  private storage), so a `401` seen by the extension is acted on by the app.
- On success: store the token, clear `renewalNeeded`, flush the queue.
- Never throws. Failures map to `RegisterResult` values (existing ones plus `notLoggedIn`, `alreadyRegistered`).
- Suggested call sites (documented, the app decides): app start or foreground, and right after login. `register(idToken)`
  stays for an explicit registration. `logout()` stays required on user switch (FR-8): it clears the token, so the
  next `ensureRegistered` registers the new user.
- `RefreshGate` and the refresh logic in both `EventSender`s are removed.

### 3.3 iOS specifics (D7)

- `ReliablePushOptions.extensionSendTimeout` default 2 s (max stays 25 s). The settings read stays capped at 2 s and
  counts against the same budget, so the extension hands the notification back within about `timeout + 0.5 s` in
  every case.
- Order in `didReceive`: `rp_tid` check → lazy configuration → `customize` → registered check → settings gate →
  persist `DELIVERED` → one send → `contentHandler`. Any error thrown inside SDK code → `contentHandler` with the best
  content so far, immediately. A crash in the host's `customize` closure cannot be caught. iOS then shows the original
  content, as documented today.
- No change to `serviceExtensionTimeWillExpire` or to exactly-once handler delivery.

### 3.4 Android specifics (D8)

- New order in `handle`: `rp_tid` check → state lookup → gate (`NotificationPoster` pre-checks split out as
  `canShow()`) → persist `DELIVERED` (off the main thread as today) → post → schedule the immediate send.
- The whole body runs inside a `try/catch (Throwable)`. If anything before the post throws, the SDK still posts a
  minimal notification: data `title`/`body`, else the app label, on the configured channel, with the `rp_tid` tap
  extra. If that minimal post also throws, `handle` returns `false` and the host may show its own notification. If
  the post itself fails after `DELIVERED` was persisted, the event stays and no fallback fires (D8, documented).
- `handle` keeps its signature and return value. `true` means posted, `false` means not ours or not shown.
- The data contract is unchanged: `rp_tid`, `title`, `body`, high priority, no `notification` block.

## 4. Payload jar `reliable-push-payload`

### 4.1 Module

- New Maven module `payload-java/` at the repo root (like `client-java/`), artifact
  `io.reliablepush:reliable-push-payload`, package `io.reliablepush.payload`.
- **Java 8 bytecode** (`maven.compiler.release` 8), **zero runtime dependencies**, no network, no threads, no
  reflection. All classes are immutable and thread-safe. Tests use JUnit 5 and AssertJ (test scope only).
- CI runs its tests on JDK 8 and JDK 21. `client-java` does not depend on it; a sender may use either or both.

### 4.2 API

```java
public final class TrackingIds {
    public static String newId();                                  // random UUID v4, lower-case
    // any case is valid; every builder embeds rp_tid lower-cased (the backend's and the SDKs' form)
    public static boolean isValid(String id);
}

public final class ApnsPayloads {
    /** Full APNs payload: aps.alert {title, body}, mutable-content 1, rp_tid, optional custom top-level keys. */
    public static String build(String trackingId, String title, String body, Map<String, ?> custom);
    /** Adds mutable-content and rp_tid to the sender's own payload; requires a visible aps.alert. */
    public static String decorate(String apnsJson, String trackingId);
    public static Map<String, Object> decorate(Map<String, ?> apnsPayload, String trackingId);
}

public final class FcmPayloads {
    /** Full FCM HTTP v1 message: message.token, android.priority HIGH, data {rp_tid, title, body, custom...}. */
    public static String build(String fcmToken, String trackingId, String title, String body, Map<String, String> data);
    /** Data map only, for client libraries such as the Firebase Admin SDK (Message.builder().putAllData(...)). */
    public static Map<String, String> data(String trackingId, String title, String body, Map<String, String> data);
    public static final String ANDROID_PRIORITY = "HIGH";
    /** Converts the sender's own FCM v1 message (notification + data) into the tracked data-only form. */
    public static String decorate(String fcmV1Json, String trackingId);
}

public final class PayloadException extends IllegalArgumentException {
    public Code code();                                            // enum, see 4.3
}
```

`decorate(String, ...)` parses the JSON with a small internal parser (adapted from `client-java`'s `Json`, written
for Java 8). Output is compact JSON, keys in input order, with reliable-push keys appended.

### 4.3 Validation (fail fast, nothing silently dropped)

| Code | When |
|---|---|
| `INVALID_TRACKING_ID` | not a UUID |
| `RESERVED_KEY` | the sender's data or custom keys contain `rp_tid` (any platform) or `title`/`body` (FCM data) |
| `APNS_NO_ALERT` | `decorate`: no visible `aps.alert` (for example a `content-available`-only payload) |
| `APNS_TOO_LARGE` | result above 4,096 bytes |
| `FCM_NON_STRING_DATA` | a data value is not a string |
| `FCM_UNSUPPORTED_NOTIFICATION_FIELD` | `decorate`: `notification` or `android.notification` holds a field other than `title` and `body` (image, channel, click action...); the message lists the fields |
| `FCM_NO_NOTIFICATION` | no visible title or body (both null or empty, for example a silent data-only message): it stays untracked, never becomes a blank notification (final review, 2026-11-08) |
| `FCM_TOO_LARGE` | result above FCM's 4,096-byte data limit |
| `INVALID_JSON` | `decorate`: input is not a JSON object |

The documentation tells the sender to catch `PayloadException` and send the push untracked, after skipping the
registration or cancelling it with `DELETE /v1/notifications/{trackingId}`. A tracked-but-unsendable push must never
become a fallback.

### 4.4 Examples in the docs

The integration guide shows the jar with raw HTTP/2 for APNs, with the Firebase Admin SDK (`putAllData`,
`AndroidConfig.Priority.HIGH`) and with Pushy, a few lines each, plus `client-java`'s register call with `trackingId`
and a 1 s timeout.

### 4.5 Golden vectors for other languages

`payload-java/src/test/resources/vectors/*.json`: each file holds an input (operation, arguments) and the exact
expected output or error code. The jar's tests run them all. `docs/integration-guide.md` links them, so a Node, .NET or
PHP backend can implement the same rules and check them against the same files.

## 6. Harness and E2E

- The console's payload preview uses the payload jar (replaces `PayloadPreview`'s APNs and FCM v1 builders; the v2
  preview stays as documentation of the future shape).
- The fake sender generates the tracking id with the jar and registers with `trackingId`.
- New E2E scenarios: `no-device-registered` (no fallback, state final), `client-tracking-id` (idempotent retry with
  the same id), `registration-lost` (push sent with an unregistered `rp_tid`: event `NOT_FOUND`, no fallback),
  `token-grace` (expired token inside the grace period delivers; past the grace period `401`, event kept queued).
- Device simulator: no token refresh on the event path, the same as the SDKs.

## 8. Incompatible changes (pre-1.0)

- SDKs no longer renew the token on their own. Apps must call `ensureRegistered` (or `register`) from time to time;
  the guide says where.
- iOS `extensionSendTimeout` default 5 s → 2 s.
- New notification state `NO_DEVICE_REGISTERED`: clients that switch over states must handle it.
- New `RegisterResult` cases `notLoggedIn` and `alreadyRegistered` (Swift enum, Kotlin sealed type): exhaustive
  `switch`/`when` in host code must handle them.
- `POST /v1/notifications` for a user without an active device no longer schedules a fallback.
- `POST /v1/notifications` requires the sender's `trackingId` (`400` without it). A repeated `externalId` with another
  `trackingId` is `409` instead of returning the existing record.
- Admin overview and daily statistics gain `noDeviceRegistered`; their rates leave those notifications out of the
  denominator.
- `rp_notifications_registered_total` gains the tag `outcome` (`pending` or `no_device_registered`).
- Android `handle` records `DELIVERED` before posting.

## 9. Requirements changes

- **FR-1** (changed): the sender registers each tracked push via an API **before sending it**, supplying the
  `trackingId` it embeds in the payload. A payload library builds the payload and the id.
  reliable-push does not send pushes itself.
- **FR-5** (changed): token renewal happens only in an app-initiated, asynchronous `ensureRegistered`, never on the
  push receive path.
- **FR-6** (changed): `DELIVERED` is recorded first and sent at once, with no token renewal. On iOS the notification
  is handed back when the send ends or after a bounded timeout (default 2 s).
- **NFR-2** (changed): "plus rare token renewals" becomes "token renewals only from `ensureRegistered`".
- **FR-20** A notification registered for a user with no active device is stored closed as `NO_DEVICE_REGISTERED`
  and never triggers a fallback.
- **FR-21** The events and logout endpoints accept a device token expired by at most a per-app grace period
  (default 90 days).
- **FR-22** A standalone Java 8+ library with zero dependencies builds and validates tracked APNs and FCM payloads
  and generates tracking ids; golden vectors define the rules for other languages.
- **FR-23** The SDK's tracking never prevents or delays display beyond the bounded iOS timeout: any SDK error ends in
  the notification being shown.
- **FR-24** The registration call is idempotent on the sender-supplied `trackingId`.
